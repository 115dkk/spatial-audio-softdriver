# 0012. 클럭 교차를 양이 2채널 뒤에 둔다

상태: 채택, 2026-10-11 (설계서 후보 3). 같은 날 M2 하드웨어 시험 뒤 제어 대상과 이득을 고쳤습니다(아래 '수정').

## 배경

가상 장치와 출력 장치는 서로 다른 클럭으로 돌기 때문에 보정이 반드시 필요합니다. 구축기는 렌더링 전의 22채널을 Python에서 싱크 리샘플링하므로, GIL과 GC가 있는 런타임이 10 ms 지터버퍼 안쪽의 실시간 루프에 들어가 있습니다.

## 결정

해체부터 컨볼루션, 리미터까지를 소스 클럭 도메인에서 끝내고, 2채널 교차 링에서 DAC 클럭과 만나게 합니다. 보정은 두 전략 중 하나로 합니다.

- ASRC: 2채널 리샘플러(rubato)의 비율로 보정합니다.
- 트림: 드라이버에 ppm을 보내 소스의 생산 속도를 DAC에 맞추고, 리샘플링 자체를 없앱니다. 소스와 출력 장치의 명목 레이트가 같을 때만 씁니다.

두 전략은 같은 수위 측정과 PI 제어기를 공유합니다. 수위는 대기 중이 아니라 출력 주기마다 잽니다(구축기에서 resync를 없앤 수정과 같은 원리). 트림을 지원하지 않는 캡처 어댑터(덤프, SAL 링)를 만나면 엔진은 ASRC로 넘어갑니다.

## 결과

- ASRC 연산이 22채널에서 2채널로 줄고, 지터와 드리프트에 관한 지식이 교차 링 한 곳에 모입니다.
- 어댑터가 둘이니 진짜 시임입니다. 블록 단위로 들어오고 주기 단위로 나가는 교차 링 시뮬레이션 하나로 두 전략을 ±300 ppm까지 함께 검증합니다.
- 출력 스레드는 링 읽기와 리샘플만 하므로 3 ms 주기 안에서 여유가 큽니다.

## 수정 (2026-10-11, M2 하드웨어 시험)

처음 구현은 출력 주기마다 잰 순간 수위를 PI 제어기에 바로 넣었고, 이득은 비례 1 ms당 2,000 ppm, 적분 200 ppm/(ms·s)였습니다. 그런데 블록은 통째로 들어오므로(PCM과 MAT는 10 ms, E-AC-3는 32 ms) 수위는 블록 크기만큼 오르내리는 톱니 모양이고, 이 이득으로는 클럭 오차가 없어도 보정값이 ±2,000 ppm 상한 사이를 오갔습니다. ASRC라면 음정이 0.2% 폭으로 흔들립니다. 당시 시뮬레이션은 수위를 매끄러운 실수로 다뤄서 이 결함을 잡지 못했습니다.

고친 내용은 다음과 같습니다.

- 제어 대상을 바닥으로 바꿨습니다. 주기마다 소비하고 남은 수위의 최저값을 0.2초 창으로 모으고, 창마다 한 번 제어합니다. 바닥은 다음 블록이 들어오기 직전의 여유라서 끊김을 직접 예고합니다. `target_ms`는 이제 이 바닥의 목표입니다.
- 이득은 비례 60 ppm/ms, 적분 3 ppm/(ms·s)입니다. QPC로 도는 소스와 USB DAC 수정 발진기의 차이는 ±100 ppm 안팎이고, ±2,000 ppm 상한은 과도 상태만 막습니다.
- 시작할 때, 끊긴 뒤, 장치 재시작 뒤(ADR 0019)에는 '목표 + 블록 하나 + 주기 하나'가 찰 때까지 무음을 내고, 그다음 '목표 + 블록 하나'를 넘는 분량을 버립니다. 버리지 않으면 바닥이 최대 블록 하나만큼 높게 시작하고, 느린 제어기가 그것을 빼는 데 1분 넘게 걸립니다.
- 시뮬레이션 시험은 블록 단위 도착과 주기 단위 소비를 그대로 흉내 내고, 엔진과 같은 제어 코드(`TroughController`)를 씁니다.

개발 PC(TOPPING USB DAC)에서 페이스를 맞춘 48 kHz 덤프를 독점 모드 3 ms 주기로 25초 재생했을 때 끊김은 없었고, 보정값은 −70~−230 ppm에서 천천히 움직였습니다. 공유 모드에서는 바닥 10.0 ms, 보정 −1~−2 ppm이었습니다.

남은 한계가 하나 있습니다. 장치 주기가 소스 블록과 같으면(공유 모드 10 ms 주기에 PCM이나 MAT) 블록 도착 위상이 주기 경계를 지날 때 실제 바닥이 블록 하나만큼 바뀝니다. 측정이 틀린 것이 아니라 바닥이 실제로 그만큼 움직입니다. 이 조합에서는 바닥을 덜 촘촘하게 붙잡고, ±100 ppm에서 300초에 몇 번 끊길 수 있습니다. 독점 모드 3 ms 주기에서는 이 문제가 없습니다.
