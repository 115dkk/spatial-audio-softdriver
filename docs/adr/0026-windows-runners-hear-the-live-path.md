# 0026. Windows 러너가 가상 오디오 케이블로 실시간 경로를 듣는다

상태: 채택, 2026-10-12

## 배경

개발은 Linux 컨테이너에서 하고, Windows에서만 도는 코드(`ssr-sys`의 WASAPI, MMCSS, `ssr-live`)는 CI의 Windows 러너에서만 실행됩니다. 그런데 GitHub의 Windows 이미지에는 소리 장치가 없어서, 장치가 필요한 시험은 모두 `#[ignore]`로 빠져 있었고 실시간 경로 전체를 돌리는 시험은 개발 PC에서만 돌았습니다. `cfg(windows)` 코드는 Windows에서 컴파일만 되고 clippy를 거치지 않았습니다.

## 결정

- **린트:** clippy와 rustdoc을 `x86_64-pc-windows-msvc`와 `aarch64-pc-windows-msvc` 대상으로도 돌립니다. 형식 검사에는 링커가 필요 없으므로 Linux 잡에서 합니다.
- **시험 행렬:** `cargo test`와 리플레이 결정성을 Windows Server 2025(windows-latest)와 2022, 그리고 Windows 11 ARM64에서도 돌립니다.
- **가상 케이블:** audio 잡은 Windows Server 2022와 2025 러너에 VB-CABLE을 설치합니다. 렌더 엔드포인트 'Speakers (VB-Audio Virtual Cable)'에 쓴 소리가 캡처 엔드포인트 'CABLE Output'으로 돌아옵니다. 패키지는 CI가 돌 때 제작자의 사이트에서 받아 SHA-256으로 고정하고, 저장소에 넣거나 다시 배포하지 않습니다. 장치 노드는 devcon과 같은 SetupAPI 호출로 만듭니다(`tools/ci/install-virtual-cable.ps1`).
  - VB-CABLE은 Vincent Burel의 기부형 소프트웨어(donationware)이고, 라이선스는 사용과 원본 그대로의 복사를 허락하며 다른 소프트웨어의 설치 절차에 넣는 것만 막습니다. 우리는 CI에서 쓰기만 합니다.
  - Microsoft 증명 서명(attestation) 드라이버는 Windows Server에서 로드되지 않으므로, Server 러너에서 로드되는 서명을 가진 가상 장치는 VB-CABLE이 사실상 유일합니다.
- **장치 시험:** `ssr-sys`가 `#[ignore]`로 둔 시험(독점과 공유 출력의 주기, 놓친 주기 뒤 회복, MMCSS, SAL 없음)을 이 장치로 돌립니다.
- **루프백:** `ssr-live play --from-dump`로 픽스처 덤프를 그 렌더 엔드포인트에 재생하는 동안 'CABLE Output'을 녹음하고, 같은 덤프를 `ssr-replay`로 오프라인 렌더링한 결과와 비교합니다. 실시간 경로는 케이블의 클럭에 맞춰 리샘플하므로 표본 단위로 같을 수 없습니다. 그래서 50 ms 창마다 기준 신호를 녹음에서 찾아(창마다 ±64 표본 안에서 위치를 따라감) 정규화 상관이 0.95 이상인 창이 90 % 이상이어야 통과입니다. 기준 신호가 녹음의 어디서 시작하는지는 10 ms RMS 포락선의 상관으로 먼저 찾고 기준 앞 0.25 s로 다듬습니다. 파형 전체의 상관으로 찾던 때는 픽스처가 거의 주기적이라 라이브 클럭이 -609 ppm 흐르자 봉우리가 퍼져 녹음 앞의 무음에 맞춰졌습니다(공유 PCM에서 처음 650 ms가 '없어진' 것처럼 보인 원인). 그 자리에서 놓친 창은 ±50 ms 안에서 다시 찾으므로, 공유 오디오 엔진이나 녹음 쪽의 끊김 하나는 그 언저리 창만 깎습니다. 공유 모드는 장치를 처음 깨우는 경우와, 무음 공유 스트림이 렌더 엔드포인트를 미리 돌리고 있는 경우(다른 앱이 소리를 내는 데스크톱)를 둘 다 잽니다. 엔진이 만든 끊김은 ssr-live의 보고(스트리밍 중 언더런, 장치 재시작)가 0이어야 하는 것으로 따로 봅니다(`tools/ci/loopback_check.py`). 독점과 공유, PCM 7.1과 DD+ 5.1을 모두 봅니다.
- **소크:** `ssr-live play --loop --report`로 독점 5분(20 ms 주기), 10 ms 주기의 독점 2분, 공유 2분, DD+ 2분, 모든 논리 프로세서를 보통 우선순위로 바쁘게 만든 채 독점 2분, 전체 페이지 힙(`gflags +hpa`와 같은 IFEO 설정) 아래 1분을 돌립니다. 소스가 흐르는 동안의 언더런, 장치 재시작, 유실 바이트, 넘침, 장애가 하나라도 있으면 실패입니다(`tools/ci/soak.ps1`). 결과는 잡 요약에 표로 남깁니다.
- **시작과 정지:** 2초씩 60번 시작하고 멈춥니다. 독점과 공유를 번갈아 하고 뒤의 절반은 CPU 부하 아래에서 합니다. 종료 코드가 0이 아니거나 합계를 찍지 못하고 끝나면 실패입니다. 러너에서는 WER가 덤프를 남기지 않았으므로, CPU 부하 아래의 독점 실행은 cdb 아래에서 돌려 접근 위반이 나면 그 스택과 모든 스레드를 찍습니다(`tools/ci/restart-stress.ps1`).
- **충돌 덤프:** audio 잡은 `ssr-live.exe`와 `ssr-replay.exe`의 WER 로컬 덤프(전체)를 켜고, 릴리스 빌드에 줄 번호 디버그 정보를 넣습니다. 덤프가 생기면 잡 끝에서 cdb로 예외 스레드와 모든 스레드의 스택을 로그에 찍고, 덤프와 PDB를 아티팩트로 남깁니다(`tools/ci/crash-dumps.ps1`).

- **독점 주기:** VB-CABLE은 WaveCyclic 드라이버라 독점 모드 이벤트를 시스템 타이머(15.6 ms)보다 자주 보내지 않습니다. 기본 타이머에서 잰 값은 다음과 같습니다(48 kHz, 16비트).

  | 요청한 주기 | 싱크가 쓴 속도 | 재시작 |
  | --- | --- | --- |
  | 최소(3 ms) | 초당 9,181 프레임 | 333 |
  | 5 ms | 15,382 | 197 |
  | 10 ms | 31,004 | 0 |
  | 20 ms | 48,828 | 0 |
  | 40 ms | 49,745 | 0 |

  20 ms 주기에서도 이벤트가 틱에 묶여 늦게 오고, 대기가 한 번 늦으면 자동 리셋 이벤트 두 번이 하나로 합쳐져 주기를 잃습니다(놓친 주기 뒤 초당 32,473 프레임). 실제 장치는 자기 주기로 인터럽트를 내므로, audio 잡은 처음부터 끝까지 시스템 타이머를 1 ms로 붙잡아 두고 MMCSS 서비스도 미리 띄웁니다(Server 이미지는 수동 시작이라 첫 등록이 실행의 첫 1초 안에서 서비스를 깨웁니다). 타이머는 `NtSetTimerResolution`을 부른 채 잠든 프로세스 하나가 붙잡습니다(`tools/ci/timer-resolution.ps1`). `exclusive_cadence_at_each_period`가 매 실행마다 주기별 속도를 다시 찍습니다. 1 ms 타이머에서 잰 값은 3 ms 초당 14,146 프레임(재시작 88), 5 ms 23,452(74), 10 ms 48,467(0), 20 ms 48,976(0), 40 ms 49,995(0)이라 VB-CABLE은 10 ms 아래의 독점 주기를 지키지 못합니다. 그래서 짧은 주기의 소크는 10 ms로 돌리고, 장치 최소 주기(3 ms)의 독점 경로는 개발 PC의 실제 DAC에서 확인합니다. 독점 장치 시험과 루프백과 대부분의 소크는 20 ms 주기로 돌려, PCM 블록(10 ms)보다 긴 주기의 경로도 봅니다(`SSR_TEST_EXCLUSIVE_PERIOD_MS`, `ssr-live --period-ms`).

## 결과

- WASAPI 출력, 실시간 스레드, 클럭 보정, 지연 측정이 PR마다 실제 Windows 오디오 스택 위에서 돕니다. 소리가 장치까지 간다는 것도 녹음으로 확인합니다.
- 10 ms 줄처럼 재시작 없이 명목 속도의 65 %로 조용히 느려지는 장치를 지금의 싱크는 알아채지 못합니다. 대기 하나가 길어질 때만 재시작하기 때문입니다. 이 잡이 처음 드러낸 결함이므로, 싱크가 이벤트 속도를 재서 장치가 지키는 주기로 스스로 옮겨 가게 하는 일을 `sys.output_cadence_guard`로 등록합니다.
- 기준은 언더런 0입니다. CI 가상 머신의 시간 지터로 이 기준이 흔들리면, 기준을 느슨하게 하기 전에 원인(우선순위, 주기, 버퍼)을 먼저 찾습니다.
- 20 ms 독점 소크가 엔진 결함 하나를 드러냈습니다. 프라이밍이 링을 목표 + 블록(10 + 10 ms)까지만 남겨, ASRC가 첫 렌더에서 가져갈 한 주기와 필터 앞보기(약 1,090 프레임)를 채우지 못했고, 그래서 매 주기 언더런과 프라이밍을 되풀이하며 소리를 한 번도 내지 못했습니다. 지금은 목표에 블록과 그 주기가 가져갈 양 중 큰 쪽을 더해 남깁니다(`engine::a_period_longer_than_a_block_plays_after_priming`). 루프백을 Linux에서 가짜 싱크로 재현하다 결함 하나가 더 나왔습니다. 소스가 끝날 때 링에 남은 프레임이 ASRC의 다음 한 입보다 적으면 영영 소비되지 않아, 링이 비지 않고 끝난 뒤 500 ms 동안 언더런이 45~52번 쌓였습니다. 지금은 끝난 뒤의 마지막 한 입을 남은 프레임과 무음으로 채웁니다(`engine::the_end_of_a_source_drains_without_underruns`).
- 우리 드라이버는 여기서 로드할 수 없을 것이라 보았지만, 드라이버 CI의 첫 실행에서 Server 2022 러너의 커널이 시험서명 드라이버를 올렸습니다. 드라이버를 지나는 경로를 러너에서 듣는 일은 ADR 0027의 패키지 시험이 맡습니다.

## 수정 (2026-10-13, 실제 모드와 새 계수)

- 루프백, 다채널 루프백, 소크, 재시작 스트레스, 드라이버 종단 검사는 보고의 다음 값을 봅니다.
  - `output_mode`가 요청한 모드와 같아야 합니다.
  - `output_fell_back`이 거짓이어야 합니다.
  - `output_reconnects`와 `output_cadence_faults`가 0이어야 합니다.
- 독점 출력이 몰래 공유로 내려가 시험이 통과하는 일이 없어졌습니다.
- 장치를 뽑았다 꽂는 재연결, 실제 DAC의 주기 감시, 재연결 중 멈춤 응답은 러너에서 할 수 없으므로 시험서명 PC의 안내서(6-1절)에서 봅니다.

## 수정 (2026-10-14, Server 2022의 VB-CABLE 설정)

러너에 까는 VB-CABLE 패키지(Driver Pack 43)의 드라이버는 2014년의 Win7용 1.0.3.5입니다. 이 드라이버는 장치가 시작할 때 `HKLM\SOFTWARE\VB-Audio\Cable`에서 두 값을 읽습니다. 제어판이 쓰는 값과 같으며, 드라이버를 역어셈블해 확인했습니다.

| 값 | 뜻 | 값이 없을 때 |
| --- | --- | --- |
| `VBAudioCableWDM_SR` | 케이블 안의 표본율. 44100, 48000, 88200만 받습니다 | 96000 |
| `VBAudioCableWDM` | 파이프 크기(내부 표본율의 표본 수). 512~8192로 자릅니다 | 7168 |

기본값에서는 케이블이 96 kHz로 돌아갑니다. 그래서 우리의 48 kHz 스트림은 렌더 쪽에서 올려 바꾸고 캡처 쪽에서 다시 내려 바꾸는데, 이 일을 케이블의 커널 타이머 경로가 맡습니다. VB-Audio가 권하는 파이프 크기는 클라이언트가 넘기는 가장 큰 버퍼의 세 배를 내부 표본율로 환산한 값입니다. 우리가 넘기는 가장 큰 버퍼는 40 ms 독점 주기의 1,920프레임이므로 96 kHz에서는 11,520표본이 필요한데, 이것이 드라이버 상한(8,192)을 넘습니다.

Server 2022 러너는 이 케이블과 함께 돌다가 가끔 통째로 멈췄습니다. 드라이버 종단 시험 한 번에서 우리 드라이버가 잰 커널 타이머 지연이 2초였고(VB-CABLE을 깔기 전의 흐름 검사에서는 0.8 ms), 그동안 출력 속도가 명목의 0.32배로 떨어지고 드라이버 링이 넘쳤습니다. 같은 커밋을 다시 돌리면 통과했습니다.

- **Server 2022:** 케이블을 스트림과 같은 48 kHz, 파이프 6,144표본(128 ms)으로 돌립니다. 변환이 없어지고, 40 ms 주기도 파이프 안에 들어갑니다(1,920 × 3 = 5,760). `realtime-audio.ps1 -CableRate 48000 -CableMaxLatency 6144`가 장치를 만들기 전에 두 값을 써 넣고, 설치 로그에 케이블이 쓸 값을 찍습니다.
- **Server 2025:** 기본값(96 kHz, 7,168표본)을 그대로 둡니다. 이 러너는 기본값으로 통과하고 있고, 변환이 있는 무거운 케이블도 시험에 남겨 둡니다.
- **합격 기준:** 바꾸지 않습니다. 이 설정으로도 Server 2022에서 같은 멈춤이 되풀이되면, 그때 Server 2022의 기준을 따로 정합니다.
