# 0033. 감시 프로세스는 앱을 띄우고 파이프의 심장박동으로 지켜본다

상태: 채택, 2026-10-15. ADR 0023 결정 4의 공유 메모리와 프로세스 감시를 파이프 하나로 바꿉니다.

## 배경

ADR 0023은 `ssr-guard`가 두 가지를 보라고 적었습니다. 앱 프로세스가 살아 있는지, 그리고 엔진이 나아가는지(출력 스레드가 기간마다 쓰고 캡처 스레드가 읽는지). 그 방법으로 엔진이 계수를 공유 메모리에 올리고 감시 프로세스가 앱 프로세스를 지켜본다고 했습니다. 판정의 핵심(`supervisor::guard`)은 M4 첫 조각에서 Linux 시험과 함께 들어왔고, 셸 조각(ADR 0001의 2026-10-15 보탬)은 감독자가 역할을 넘겨받기 전에 쓰는 복원점과, 종료가 제때 끝나지 않을 때 그 복원점으로 되돌리는 마지막 수단을 프로세스 안에 두었습니다. 남은 것은 앱 밖에서 지켜보는 프로세스입니다.

공유 메모리(`CreateFileMapping`, `MapViewOfFile`)와 프로세스 감시(`OpenProcess`, `WaitForSingleObject`)는 모두 격리 크레이트의 unsafe 호출이고, `ssr-sys`의 예산 40 가운데 39가 쓰였습니다(ADR 0032). 토스트 알림은 WinRT 바인딩의 안전한 호출과 기존 COM 아파트먼트 래퍼를 써서 새 unsafe 없이 보낼 수 있습니다(아래 보탬).

## 결정

- **감시 프로세스가 앱을 띄웁니다.** `ssr-guard.exe`가 `spatial-softreceiver.exe --guarded`를 자식으로 띄우고 그 표준 출력을 파이프로 받습니다. 앱은 1초마다 심장박동 한 줄(`ssr_types::app::Heartbeat`: 감독자가 Running인지, 엔진의 출력 기간 계수와 캡처 읽기 계수)을 씁니다. 파이프의 EOF가 앱의 종료이고, Running인데 줄이 2초 동안 없거나 계수가 2초 동안 그대로면 멈춤입니다. 프로세스 핸들도 공유 메모리도 unsafe도 필요 없습니다.
- **사용자가 앱을 바로 실행하면** 앱은 Tauri를 만들기 전에 감시 프로세스를 분리해 띄우고 곧바로 끝나며, 감시 프로세스가 앱을 `--guarded`로 다시 띄웁니다. 감시 프로세스를 띄우지 못하면 로그에 적고 감시 없이 돕니다. `--smoke`(CI)와 `--guarded`로 뜬 앱은 감시 프로세스를 띄우지 않습니다. 로그인 자동 시작의 `--minimized`는 그대로 전달됩니다.
- **엔진의 계수**는 `EngineStatus`의 `output_periods`(출력 스레드가 마친 기간, 무음 포함)와 `capture_reads`(돌아온 읽기, 0바이트 포함)이고, 실시간 스레드가 원자 변수에 더하기만 합니다.
- **판정과 행동**은 ADR 0023 그대로입니다. 첫 멈춤에는 앱을 죽이고, 복원점이 있으면 역할을 되돌린 뒤(`restore_point::restore`), 앱을 `--guarded --resume`으로 다시 띄웁니다. `--resume`으로 뜬 앱은 Ready이면 스스로 켭니다(역할을 새로 넘겨받음). 두 번째 멈춤이나 앱의 종료에는 복원점이 있으면 되돌리고 끝납니다. 복원점이 없는 종료는 정상 종료이고 감시 프로세스도 0으로 끝납니다. 앱이 Running이 아니라고 말하면(꺼짐, 설정 중, 종료 중) 멈춤 시계만 멈추고, 한 번뿐인 재시작은 쓴 채로 남습니다. 다시 띄운 앱이 첫 줄을 쓰기 전의 침묵은 멈춤이 아닙니다.
- **역할을 쥔 채 Running이 되지 못한 앱.** 제어 스레드는 역할을 넘겨받고 엔진을 띄우는 일을 한 걸음으로 하고, 종료할 때도 엔진을 멈추고 역할을 되돌리는 일을 한 걸음으로 합니다. 그 사이에는 심장박동이 없으므로, 복원점이 있는데(역할을 쥔 상태) Running 심장박동이 없는 침묵이 15초를 넘으면 그 걸음이 굳은 것입니다. 15초는 마지막 심장박동 뒤에 감시 프로세스가 역할을 쥔 것을 처음 본 때부터 셉니다. 역할을 쥐기 전에 걸린 시간(느린 장치 조회)은 세지 않습니다. 이때는 다시 띄우지 않고 앱을 죽이고 되돌린 뒤 끝냅니다(표지의 까닭 `stuck`). 소리를 낸 적이 없는 앱을 다시 띄울 까닭이 없고, 종료 중에 굳은 앱을 다시 띄우면 사용자의 뜻과 어긋나기 때문입니다. 제어 스레드는 Disable과 Quit를 처리하기 전에 Running이 아니라는 심장박동을 한 줄 먼저 써서, 엔진을 멈추고 역할을 되돌리는 걸음이 Running 중의 멈춤으로 잡혀 사용자가 끈 엔진이 다시 켜지는 일이 없게 합니다. Running 중에 프로필을 다시 준비할 수 있는 의도(`ImportBrir`, `SetProfileKind`, `SetSpeakerLayout`, `ImportCorrection`, `ClearCorrection`, ADR 0034)도 같은 줄을 먼저 씁니다. 실행 중인 엔진에 넘길 프로필을 제어 스레드가 그 자리에서 준비하므로(디코드, 리샘플, 접기, FFT) 2초를 넘길 수 있기 때문입니다. 그 걸음의 침묵은 역할을 쥔 침묵으로 15초 한도에 걸리고, 걸음이 끝나면 결과와 상관없이 심장박동을 곧바로 한 줄 다시 씁니다. 엔진이 `NeedsPrepared`로 출력을 다시 달라고 할 때도 같습니다. 감독자의 `tick`은 그것을 기억만 하고, 제어 스레드가 Running이 아니라는 줄을 쓴 뒤 `prepare_again`으로 지금 재생하는 프로필을 다시 준비하고, 끝나면 심장박동을 다시 씁니다. 변경 큐가 준비한 출력을 거부하면 그 출력은 감독자가 보관하고 다음 틱에는 전달만 다시 시도합니다. 이 빠른 재시도는 심장박동을 바꾸지 않아, 큐를 비우지 못하는 실제 엔진 멈춤의 시계가 계속 흐릅니다. 틱 안에서 준비해 버리면 큰 BRIR 세트를 준비하는 몇 초가 2초 멈춤으로 잡혀 감시 프로세스가 앱을 죽이기 때문입니다. 준비를 다른 스레드로 옮기는 길은 그동안 들어온 가져오기와 순서를 맞춰야 해서 쓰지 않습니다. 제어 스레드가 뜰 때도 한 줄 씁니다.
- **복원점에는 주인이 있습니다.** 감독자는 복원점에 자기 프로세스 id(`app_pid`)를 적습니다. 감시 프로세스는 `app_pid`가 0이거나 자기가 띄운 자식의 것일 때만 그 복원점을 쓰고, 다른 프로세스의 복원점은 건드리지 않습니다. 앱을 띄우지 못한 감시 프로세스는 아무것도 되돌리지 않습니다. 죽은 인스턴스가 남긴 복원점과 살아 있는 인스턴스의 복원점을 가릴 수 없기 때문이고, 죽은 인스턴스의 것은 다음에 뜨는 앱이 거둡니다. 감시 프로세스만 죽고 앱이 살아 있을 때 사용자가 앱을 다시 실행하면, 새 감시 프로세스의 자식은 단일 인스턴스 규칙으로 바로 끝나는데, 그 EOF로 살아 있는 앱의 역할을 되돌리면 안 되기 때문입니다.
- **감시 프로세스는 상태 디렉터리마다 하나입니다.** 감시 프로세스는 `guard.lock`을 잠그고 시작하며(OS가 프로세스와 함께 푸는 파일 잠금), 잠그지 못하면 다른 감시 프로세스가 앱을 쥔 것입니다. 사용자가 앱을 한 번 더 실행하면 새 앱이 새 감시 프로세스를 띄우는데, 잠금을 얻지 못한 감시 프로세스는 앱을 띄우지 않고 상태 디렉터리에 창을 열어 달라는 파일(`show-window`)을 쓰고 끝납니다. 실행 중인 앱의 셸이 1초마다 그 파일을 거두어 창을 엽니다. 앱을 하나 더 띄워 단일 인스턴스 규칙에 맡기는 방법은 두 감시 프로세스가 거의 동시에 뜰 때 어느 쪽의 앱이 남을지 정할 수 없어 쓰지 않습니다. 잠금 파일 자체가 열리지 않으면 기록하고 그냥 감시합니다. 복원점의 주인 규칙이 살아 있는 앱의 역할을 지킵니다.
- **알림은 표지 파일입니다.** 감시 프로세스가 되돌리거나 다시 띄우면 `guard-restored.json`(까닭, 시각, 복원 메모)을 쓰고, 앱은 다음에 뜰 때 그것을 읽고 지운 뒤 스냅샷의 `notes`에 한 문장으로 올립니다. 표지를 쓰는 모든 경우에 같은 문장으로 Windows 토스트도 보냅니다. 표지 기록이 실패해도 토스트는 시도하고, 토스트 실패는 `guard.log`에만 남겨 복원과 종료 코드를 바꾸지 않습니다. 문장은 `ssr_guard::marker::sentence` 한 곳에서 만들고, 복원 메모는 기존처럼 스냅샷의 별도 notes로 남깁니다.
- **앱이 뜰 때 복원점이 남아 있으면**(지난 인스턴스가 역할을 쥔 채 죽었고 감시 프로세스도 없었던 경우) 셸이 감독자를 만들기 전에 그 복원점으로 되돌립니다. 감독자는 늘 깨끗한 상태에서 시작합니다.
- `ssr-guard`의 판정 루프(`runner`)는 줄의 출처와 시계와 플랫폼을 트레이트로 받아 Linux에서 시험하고, Windows 쪽은 앱을 띄우고 죽이는 것과 `WindowsHost`로 되돌리는 것뿐입니다. CI는 driver.yml의 시험서명 설치 잡에서 가짜 앱(`tools/ci/fake_app.py`)으로 종료, 멈춤, 정상 종료의 세 시나리오를 돌려 역할이 돌아오는지 `ssr-live host show`로 확인합니다(`tools/ci/guard_check.py`).

## 결과

- unsafe 예산을 쓰지 않고 ADR 0023의 감시가 들어옵니다. 앱이 어떻게 죽어도(패닉, 강제 종료, 전원 끊김은 제외) 기본 장치가 우리 엔드포인트에 남지 않습니다.
- 앱의 프로세스 부모가 감시 프로세스가 됩니다. 작업 관리자에는 둘이 보입니다. 감시 프로세스는 앱이 정상 종료하면 함께 끝납니다.
- 심장박동은 앱의 제어 스레드가 쓰므로, 제어 스레드가 굳으면 계수가 있어도 멈춤으로 잡힙니다. 그것도 의도한 것입니다. 드라이버 설치처럼 제어 스레드가 오래 막히는 일은 역할을 쥐기 전의 일이라 복원점이 없고, 그래서 침묵이 멈춤으로 잡히지 않습니다.
- 감시 프로세스의 기록은 상태 디렉터리의 `guard.log`입니다. 앱의 `app.log`와 같은 디렉터리라 문제를 보고할 때 함께 모읍니다.
- 설치본(다음 조각)은 `ssr-guard.exe`를 앱 옆에 두고, 아래 AUMID 바로가기 조건을 갖춥니다.

## 2026-10-15 보탬: 되돌렸을 때의 토스트

- `ssr_sys::toast`는 `windows` 크레이트의 `XmlDocument::LoadXml`, `ToastNotification::CreateToastNotification`, `ToastNotificationManager::CreateToastNotifierWithId`로 제목과 본문 한 줄씩을 보냅니다. XML 특수 문자는 플랫폼 독립 함수에서 이스케이프하며 Linux 시험으로 확인합니다. 기존 `ComGuard`로 MTA에 들어가는 감시 프로세스 스레드에서 호출하고, 사용자의 클릭이나 닫기를 기다리지 않습니다. `Show`의 성공은 Windows 알림 설정에 따른 실제 표시까지 보증하지 않습니다.
- 셸 설정 때 `register`가 사용자 권한으로 `HKCU\Software\Classes\AppUserModelId\io.github.115dkk.spatial-softreceiver`의 `DisplayName`과 `IconUri`를 덮어써 등록합니다. AUMID는 `tauri.conf.json`의 identifier와 같습니다. 레지스트리 FFI에 새 unsafe를 쓰지 않도록 시스템의 `reg.exe`를 셸 없이 인자별로 호출하고, 콘솔 창과 표준 출력을 막습니다. 등록 실패는 앱 로그에만 남깁니다.
- **레지스트리 표시 정보만으로 토스트 조건을 갖췄다고 보지 않습니다.** Microsoft Learn의 [AUMID로 데스크톱 토스트를 켜는 방법](https://learn.microsoft.com/en-us/windows/win32/shell/enable-desktop-toast-with-appusermodelid)은 유효한 시작 메뉴 바로가기가 필요하고 설치본에서 만들기를 권합니다. [데스크톱 토스트 전송](https://learn.microsoft.com/en-us/windows/win32/shell/quickstart-sending-desktop-toast)은 바로가기의 `System.AppUserModel.ID`와 `CreateToastNotifier`에 넘기는 값이 같아야 한다고 명시합니다. 시작 메뉴에 고정할 필요는 없습니다.
- 따라서 설치본은 앱의 시작 메뉴 바로가기에 `System.AppUserModel.ID = io.github.115dkk.spatial-softreceiver`를 넣어야 합니다. 이번 조각은 바로가기 생성과 활성화 COM 서버 등록을 하지 않습니다. 토스트를 눌렀을 때 앱을 띄우는 동작은 제공하지 않으며, 설치본에서 알림의 실제 표시와 아이콘을 Windows 데스크톱에서 시험해야 합니다. `IconUri`에는 앱 옆의 `spatial-softreceiver.ico`(설치본이 둠)를 넘기고, 없으면 등록에서 뺍니다. 설치본에서 아이콘이 실제로 보이는지 검증해야 합니다.
- 작업서의 [다른 비패키지 앱의 토스트 문서](https://learn.microsoft.com/en-us/windows/apps/design/shell/tiles-and-notifications/send-local-toast-other-apps)는 확인일에 404를 반환했습니다. 검색 결과에는 `CustomActivator`를 포함하는 레지스트리/COM 등록 경로가 나오지만, 이를 생략한 HKCU의 `DisplayName`, `IconUri` 두 값만으로 충분하다는 근거로 삼지 않았습니다. 위의 확인 가능한 바로가기 기반 계약을 따릅니다.
