# 0018. 개발용 실시간 앱 ssr-live를 둔다

상태: 채택, 2026-10-11

## 배경

M2의 끝나는 조건은 시험서명 PC에서 게임과 Apple Music을 실제로 듣고, 지연이 구축기 이하인지 숫자로 확인하는 것입니다. 그런데 설계서의 앱 목록(`spatial-softreceiver`, `ssr-setup`, `ssr-replay`)에서 실시간으로 소리를 내는 앱은 M4의 Tauri 앱뿐입니다. 게다가 MAT 디코더와 블랙박스 골든은 SAL 링에서 녹화한 덤프가 있어야 만들 수 있는데(ADR 0005), 그 덤프를 녹화할 도구가 없습니다.

## 결정

`apps/ssr-live`라는 명령줄 개발 도구를 둡니다.

- `ssr-live record`: SAL 링(`ssr-sys::sal`)에서 받은 기록 스트림을 그대로 덤프 파일(`.ssrdump`)로 씁니다. 소리는 내지 않습니다. MAT 디코더와 골든을 위한 입력을 만드는 것이 이 명령의 목적입니다.
- `ssr-live play`: SAL 링 → 엔진 → WASAPI로 실제 소리를 내고, 지연 p50/p99, 교차 링 바닥, 끊김 횟수, 장치 재시작 횟수, 클럭 보정량을 1초마다 표시합니다. `--record`를 주면 같은 스트림을 덤프로 함께 녹화합니다.
  - `--from-dump`는 SAL 링 대신 덤프를 기록된 QPC 간격대로 흘리고 각 기록의 QPC를 내보낸 시각으로 새로 찍습니다. SAL이 없는 PC에서도 실시간 경로 전체(실시간 스레드, WASAPI, 클럭 보정, 지연 측정)를 돌려 볼 수 있습니다. 소스 클럭은 QPC가 됩니다.
  - `--mute`는 모든 처리를 그대로 하되 장치에는 무음을 보냅니다.
- `ssr-live devices`: 출력 장치 목록을 보여 줍니다.

SAL 링은 관리자 권한이 있어야 열리므로 `record`와 `play`는 관리자 창에서 돌립니다. 이것은 개발용 SAL 드라이버의 제약이고, 우리 드라이버(M3)는 일반 사용자에게 엽니다(ADR 0011).

## 결과

- ssr-live는 `ssr-sys`를 링크하는 개발 도구입니다. 정책 게이트가 허용하는 범위(apps 아래의 앱)에 들고, `ssr-replay`처럼 Linux CI에서 돌지는 않습니다.
- 릴리스 워크플로는 ssr-live를 패키징하지 않습니다. SAL 드라이버를 가진 개발 PC에서만 의미가 있기 때문입니다. 필요하면 CI 산출물로만 받습니다.
  - 2026-10-12 고침: SAL을 깐 시험서명 PC를 가진 분이 릴리스를 받아 M2의 남은 시험(SAL 링 녹화, 듣기, 지연)을 맡습니다(`docs/testing/test-signed-pc.md`). 그래서 릴리스의 Windows 도구 zip에 ssr-live를 싣습니다. SAL이 없는 PC에서는 `record`와 `play`가 SAL 장치를 찾지 못했다고 끝나므로 다른 사람에게 해가 없습니다.
- M4에서 Tauri 앱이 생기면 ssr-live의 엔진 배선은 supervisor로 옮겨 가고, `record`는 앱의 진단 녹화가 대신합니다. 그때 이 앱을 지울지 다시 정합니다.
- 2026-10-13 고침: 우리 드라이버가 생겼으므로 `record`와 `play`는 `--source driver|sal`을 받고, 기본은 `driver`(`\\.\SpatialSoftReceiver`, `ssr-sys::driver_ring`)입니다. SAL은 `--source sal`일 때만 엽니다. 시험 안내서의 SAL 명령도 이것을 씁니다.
  - `--endpoints`는 엔드포인트의 임의 부분집합을 받습니다(예: `0,2`).
  - `devices`는 드라이버의 엔드포인트 마스크와 QPC 주파수, 그리고 엔드포인트마다 켜진 코덱과 PCM 규칙(표본율, 표본 모양, 마스크 채널 상한, 직접 출력 채널 수)도 보여 줍니다(ADR 0024).
  - `play`는 `--direct-layout <채널 수>=<프리셋|이름,...>`으로 채널 마스크가 0인 PCM의 직접 배치를 정합니다. 여러 번 줄 수 있습니다(ADR 0029의 2026-10-13 고침).
  - 녹화는 덤프 형식 2로 READ 경계를 남깁니다(ADR 0024). 지금은 볼륨 기록이 32채널인 형식 3으로 씁니다.
  - `play --record`의 녹음 고리가 차서 버린 READ는 `RECORDER_GAP`과 보고의 손실 바이트로 드러납니다.
  - 보고 JSON에는 드라이버 통계(`GET_STATS`)의 처음과 끝 차이가 들어갑니다.
